# Restream connection: narrow, useful, optional

Official reference: [Restream MCP server](https://developers.restream.io/mcp-server). Endpoint: `https://mcp.restream.io/mcp`, OAuth authorization through the client. Discover actual tool schemas; menu labels and availability vary.

The live server exposes 30 tools; use the schema the host actually shows. It never accepts passwords or RTMP/SRT credentials and does not return stream keys. Configure manual channel credentials in the dashboard, not in an MCP prompt. See [route diagnosis](route-diagnosis.md) before interpreting a missing feature as an account fault.

Useful read sequence, scoped to the problem:
1. Find the relevant connected channel and event with `list_channels` and, when necessary, `list_user_events`.
2. Check `check_channel_api_access` for account authorization problems.
3. Inspect `get_event` and `list_event_destinations` for the correct event's destinations. Scheduled, draft and missed events return the full list. Finished events return only part of it (seen live: 1 of 9 destinations on one show, none on another), so never read a finished show's list as the answer and never say "it went to <platform> only". Always run the recovery in the shared event-lookup reference (the same-title Studio draft clone, then the analytics `byChannel` keys mapped through `list_channels`), merge every source, and say "Restream returns only part of the platform list for finished streams". Whether live events return the list is unverified (if empty, ask which platforms are on; never treat the set as empty). Map every destination `channelId` through `list_channels`: the Restream Webinar page is a listed channel there (platform "unknown", platformId 85, display name "Webinar"), labelled "Restream Webinar". A channel still unmatched is "a channel not in your channel list".
4. Use `check_event_channels_activation` to check plan activation constraints, with the complete channel set, including the Restream Webinar page when it is already on the event (the check accepts it; verified on a 9-destination draft). Only a destination with platform "unknown" and platformId 85 that has no matching channel in `list_channels` (older data) is left out, and say so. It reports one violation at a time; only a result carrying `upgradeUrl` or a reason that names a plan, add-on or upgrade is a plan gate. Treat `upgradeUrl` only as the signal that a gate was hit; never show or link it. Use the read-only copy from the shared plans-and-paywalls reference (its plan-limit message for `channels_count_too_much`, its gate copy for a channel type), linking only the pricing page. `check_channel_api_access` reports the Webinar page as `not_checkable` ("added manually"): that is expected for a webinar page, never a fault, never a manually added channel, and never a reason to suggest a test stream.

Successful access or activation is evidence only for that check. It is not proof of media delivery, encoder health or platform playback. Do not treat aggregate viewer/message analytics as transport statistics. Current documented tools cannot inspect/control local OBS, OS devices, browser permissions, routers, or detailed live ingest health. Never claim a Restream connection that is not actually available in the current chat.

This skill makes no Restream changes. Destination toggles or event edits go to restream-manage-stream as a fix list with an actual target and a concrete reason. Preserve working destinations and keep secrets out of prompts. If a tool or connector is unavailable, continue with manual observations. Do not invent replacement calls.

The [SRT documentation](https://support.restream.io/en/articles/9943983-how-to-stream-to-restream-using-srt) separately describes live channel status, ingest bitrate and FPS in the UI/public API. That does not expose equivalent tools through the documented MCP surface. Use the actual authorized capability if available, or request a redacted monitor screenshot. Failover/backup status is not documented as available through that API.
